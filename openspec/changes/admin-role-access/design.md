# Design

## Context

平台无角色体系，字典写与 LLM 凭据对所有登录用户开放（此前两个变更的显式取舍）。用户要求收紧为仅管理员，并预置默认管理员 `admin@qq.com / admin123`。

## Goals / Non-Goals

Goals:

- 最小角色模型：一个布尔标记，不做完整 RBAC
- 默认管理员幂等种子（应用启动时，非迁移）
- 设置端点权限收紧 + 前端入口控制

Non-Goals:

- 完整角色/权限管理界面（角色的创建与分配仍需改代码或直接改库）
- 管理员后台（用户列表、强制下线等）
- 密码强度策略对种子账号的适用（用户显式指定弱密码，风险已记录）

## Decisions

### 1. 角色建模：`users.is_admin` 布尔列，不做角色表

当前只有两种角色且无权限组合需求。布尔列 + 查询即够；未来如需多角色再演进为关联表。

### 2. 默认管理员在应用启动时幂等创建（lifespan），不在迁移中

- 迁移中生成 Argon2 哈希需要迁移依赖应用代码，且哈希不可逆导致"已存在则跳过"的判断仍需应用逻辑
- 启动时 `ensure_default_admin`：按邮箱查询，不存在才创建（`email_verified=True`、`is_admin=True`）；存在则完全不动（用户改过密码也不重置）
- 与「库结构只通过迁移变更」的约束不冲突：这是种子数据而非结构

### 3. 权限依赖：`require_admin = get_current_user + is_admin 校验`

复用现有认证依赖，非管理员抛 403 `FORBIDDEN`（错误码已存在）。挂载点：字典 POST/DELETE、`GET/PUT /settings/llm`。字典 GET 保持 `get_current_user`（押题向导全用户依赖）。

### 4. 401 vs 403 的边界

未登录/令牌无效 → 401（`get_current_user` 原行为）；已登录但角色不足 → 403。前端据此区分跳登录与提示无权限。

### 5. 前端控制为体验层，接口层为安全层

设置入口 `v-if="store.isAdmin"`、路由 meta `requiresAdmin` + 守卫重定向；即便绕过前端直接调接口，服务端 403 兜底。

## Risks / Trade-offs

- [默认凭据 admin123 已随文档公开] → 仅适用于本地/内网；生产部署必须立即改密码（README 安全章节标注）
- [弱密码不满足注册校验] → 种子创建直连哈希服务，绕过注册接口的复杂度校验，属显式决定
- [角色提升无审计] → 当前无提升入口（只能改库），风险有限
- [前端缓存 KeepAlive 中的设置页] → 登出时已清空缓存，不存在跨账号残留
