# Design

## Context

后端已有统一错误处理、追踪中间件、默认拒绝的认证依赖与 Alembic 迁移基线；前端已有五项导航外壳与「简历押题」「知识库」占位页，Axios 客户端带静默续期。本变更在此之上补齐主线第一环节。数据库 PostgreSQL（开发与测试亦可用 SQLite），大模型走 OpenAI 兼容接口（用户已确认使用 DeepSeek）。

## Goals / Non-Goals

Goals:

- 简历与知识库文档的完整生命周期：上传 → 校验 → 存储 → 解析/分块 → 使用 → 删除
- 押题生成的一次完整闭环：目标信息 + 简历 + 知识库 → 大模型 → 结构化押题列表（含命中依据与元数据）
- 所有资源严格按属主隔离，删除即彻底删除
- 无模型凭据的环境下，除押题外的全部功能可开发与测试

Non-Goals:

- 面试会话、评分报告、历史回看（后续变更）
- 向量检索与 embedding（本期用关键词检索，接口预留演进）
- 简历解析的版式还原（只提取纯文本，保真排版不做）
- 多租户、对象存储直传、OCR

## Decisions

### 1. 文件存储：本地目录 + 存储接口抽象

文件保存到配置化的本地目录（默认 `backend/var/uploads`，已 gitignore），按 `{资源}/{属主id}/{uuid}{原扩展名}` 组织，数据库只存相对路径。定义 `Storage` 接口（save/read/delete），本期实现为本地文件系统，未来可替换为 S3/MinIO 而不动业务层。

备选：直接把文件二进制存数据库（备份简单但库膨胀、内存压力大）；直接对接 MinIO（多一个部署组件，骨架期过重）。

### 2. 文档解析：pypdf + python-docx + 纯文本直读

PDF 用 `pypdf`，DOCX 用 `python-docx`，TXT/MD 直接按 UTF-8 读取（无法解码视为解析失败）。三者都只提取纯文本。

备选：`pdfplumber`（版式还原更好但更重、更慢）；本期目标是"给大模型可读文本"，不需要版面坐标，故选轻量方案。

### 3. 大模型接入：LangChain ChatOpenAI + Pydantic 结构化输出

用 `langchain-openai` 的 `ChatOpenAI`，`base_url` 指向 DeepSeek（`https://api.deepseek.com`），模型名、温度、超时全部走配置。押题输出用 Pydantic 模型 + `with_structured_output` 约束为 JSON，解析失败时返回 `MODEL_OUTPUT_INVALID`（对应 spec 场景）。

备选：裸 `httpx` 调 OpenAI 兼容接口（少一层依赖但要自己处理重试与结构化解析）；选 LangChain 是用户既定技术栈，且结构化输出与提示词模板开箱即用。

### 4. 知识库检索：关键词打分，方言无关

文档切分为 300–500 字的重叠片段存表（`knowledge_chunks`），检索时按「岗位描述 + 岗位名」与片段的关键词重合度打分取 Top-N（跨 SQLite/PostgreSQL 都能跑）。检索服务定义独立接口，为后续换 pgvector / embedding 留位置。

备选：PostgreSQL `tsvector` 全文检索（性能好但 SQLite 测试环境不可用，违背"测试库方言无关"现状）；直接上向量检索（引入 embedding 模型与 pgvector，超出本期范围）。

### 5. 押题生成：同步请求，超时 120 秒

押题接口同步完成生成并返回列表（spec 场景为同步语义），前端展示"AI 分析中"loading。超时、温度、最大输出 token 均配置化。简历文本超长时按配置上限截断（默认 12000 字符），防止 token 爆炸与费用失控。

备选：两阶段（创建记录返回 ID + 后台任务 + 轮询）。体验更好但要引入任务状态机与轮询协议，且需改动 spec 场景；骨架期选择同步，后续如确有需要再演进（到时以新变更修改 spec）。

### 6. 数据模型与访问控制

- `resumes`：属主、原文件名、存储路径、体积、MIME、解析状态、解析错误、解析文本（TEXT 列）
- `knowledge_documents`：属主、名称、存储路径、体积、可见性（public/私有）、是否可检索
- `knowledge_chunks`：文档外键、片段序号、片段文本
- `predictions`：属主、目标信息快照（岗位/年限/描述/编程语言）、简历外键、模型名、提示词版本、生成时间、状态
- `predicted_questions`：押题外键、序号、题目、难度、命中依据（JSONB/JSON，含来源类型与来源标识）

所有资源端点统一「属主过滤 + 找不到返回 404」的模式（与 users 模块一致），不泄露资源存在性。

### 7. 提示词管理

提示词模板以版本号管理（常量 + 版本字符串，如 `prediction-v1`），随押题记录落库。本期不做提示词后台配置，只保证可追溯与可演进。

## Risks / Trade-offs

- [同步生成占用请求线程数十秒] → 超时 120s 上限 + 前端 loading + 服务端日志记录耗时；量级上升后再异步化
- [大模型输出偶发不符合结构] → `with_structured_output` 强约束 + 解析失败返回 `MODEL_OUTPUT_INVALID`，不让坏输出到达用户
- [简历文本超长导致 token 超限] → 按配置截断并在提示词中注明"以下为简历节选"
- [本地文件存储无副本] → 备份策略记入 README 部署说明；存储接口已抽象，迁移对象存储成本可控
- [关键词检索召回有限] → 本期定位是"最小可用知识库"；检索接口已抽象，向量检索作为后续变更
- [解析库对复杂 PDF 兼容不足] → 解析失败路径已有明确错误码与用户提示，用户可改传 TXT 版本

## Migration Plan

1. 新增 Alembic 迁移（四张表 + 索引），`upgrade head` / `downgrade -1` 双向验证（沿用现有迁移测试模式）
2. 新配置项全部带默认值（LLM 相关默认指向 DeepSeek 公网地址但无 Key），不配置 Key 不影响存量功能与测试
3. 回滚：`downgrade` 即可移除新表；上传目录独立于代码，回滚不影响存量数据

## Open Questions

- 押题数量默认值暂定 8 题、可配置（`PREDICTION_QUESTION_COUNT`），是否需要用户在界面自选数量（3/5/8/10）留待使用反馈后决定
- 知识库「公开文档」的创建入口本期仅限数据库种子或本人上传后自标公开；是否需要管理后台，待后续变更
